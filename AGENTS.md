# AGENTS.md — обязательный протокол разработки

Этот файл обязателен для любого нового чата/агента, который меняет `Gorills/novella-game`.

## Сначала прочитать

Перед изменениями агент обязан прочитать:

1. `AGENTS.md`;
2. `docs/CANON.md`;
3. `docs/03-production/EXECUTION_PROTOCOL.md`;
4. `docs/03-production/QUALITY_GATE.md`;
5. `docs/03-production/PLAYTEST_RUBRIC.md`;
6. документы, относящиеся к задаче.

Если задача касается персонажей или артов — дополнительно `docs/00-vision/VISUAL_BIBLE.md` и `docs/01-narrative/CHARACTERS.md`.
Если задача касается сюжета — дополнительно `docs/01-narrative/PROLOGUE_BEAT_SHEET.md` и релевантный раздел `STORY_OUTLINE.md`.

## Strict execution protocol — обязательный порядок работы

`docs/03-production/EXECUTION_PROTOCOL.md` является обязательным, а не рекомендательным.

Ключевые правила:

- только одна активная фаза за раз: preflight → narrative/logic implementation → logic verification → art/UI → real UI playtest → visual QA → fix → Git review → merge;
- перед первой мутацией зафиксировать актуальный SHA `main`, отдельную branch, scope, DoD и acceptance screenshots;
- после tool failure сначала диагностировать причину; запрещены слепые повторы;
- один повтор допустим только после реального изменения условий;
- один Chromium process tree на один QA-run;
- один image-generation запрос решает одну asset-задачу; мокап/постер/contact sheet не принимается вместо production asset;
- после каждой законченной фазы дать короткий checkpoint с фактическим состоянием;
- заметная visual/gameplay работа идёт только через feature branch → PR → CI → открытые screenshots → fixes → merge → проверка actual `main`;
- если gate не пройден, статус только `in progress` или конкретный `blocked`, но не `done`.

## Приоритет источников истины

При конфликте информации действует порядок:

1. последнее явное решение пользователя по этому проекту;
2. `docs/CANON.md`;
3. locked visual reference / character sheet;
4. world/character/story documents;
5. код и тестовые данные;
6. старые рабочие заметки.

Случайный текст в коде, мокапе или старом документе не может молча менять канон.

## Катерина — жёсткий visual и behavioral lock

`web/assets/katerina.webp` — канонический исходный референс Катерины.

Обязательно:

- **каре**;
- тёмно-красные волосы;
- карие глаза;
- светлая кожа;
- узнаваемое лицо и пропорции из исходного референса;
- высокая плотность татуировок;
- чёрная современная готическая одежда;
- серебряные украшения.

Запрещено:

- менять каре на длинные волосы;
- «переосмыслять» лицо;
- генерировать новую Катерину вместо locked reference без прямого запроса пользователя;
- принимать арт, где персонаж визуально стал другим человеком.

Поведенчески Катерина в начале истории — обычная 21-летняя девушка, иллюстратор и начинающий тату-мастер. Она не полицейская, не детектив, не криминалист и не опытный маг.

Нельзя заставлять её:

- ночью идти на место преступления только из любопытства;
- пересекать полицейское оцепление без чрезвычайной причины;
- трогать потенциальные доказательства как часть «gameplay»;
- делать профессиональные выводы без установленной компетенции;
- сознательно применять незнакомую магию до того, как она вообще узнала о способности.

Её наблюдательность объясняется визуальной профессией, а не скрытой криминалистической подготовкой.

## Кощей — character lock

Кощей:

- чёрный домашний кот с яркими зелёными глазами;
- до первого сверхъестественного reveal ведёт себя как обычный кот;
- впервые говорит только после домашней повторной вспышки татуировки Катерины;
- первое высказывание не разыгрывается как gag;
- не является комическим mascot или бесконечным lore dispenser;
- знает больше Катерины, но не всё и может иметь собственные мотивы.

`web/assets/koshchey.svg` — текущий visual baseline Кощея до появления отдельного утверждённого пользовательского референса.

## Definition of Done

Нельзя сообщать пользователю «готово», пока не выполнен quality gate.

Для заметной игровой/визуальной задачи обязательны:

1. реализовать функциональность;
2. запустить tests/validation;
3. реально запустить игру;
4. пройти изменённый игровой путь **реальными UI-действиями** от входа до выхода;
5. снять реальные screenshots ключевых состояний;
6. открыть и визуально просмотреть screenshots;
7. отдельно пройти `PLAYTEST_RUBRIC.md`;
8. исправить найденные проблемы;
9. повторить tests + agent smoke + UI playthrough + visual QA;
10. проверить diff и состав файлов;
11. открыть PR;
12. убедиться, что PR mergeable и проверки зелёные;
13. merge в `main`, если пользователь заранее разрешил merge;
14. проверить итоговый SHA `main` и post-merge CI;
15. только после этого считать задачу завершённой.

Если среда не позволяет выполнить один из gate-пунктов, агент обязан прямо сказать какой именно. Нельзя подменять проверку предположением.

## Четыре обязательных вердикта каждого playtest

После любого заметного изменения игрового куска агент обязан дать четыре независимых вердикта:

### Narrative Logic

Проверить:

- мотивацию каждого крупного действия;
- cause → effect;
- знания персонажа на текущий момент;
- реалистичность поведения в опасности;
- отсутствие внезапных профессиональных компетенций.

### Interest & Pacing

Проверить:

- есть ли сцены, которые существуют только как переход;
- не несутся ли reveal подряд без реакции;
- есть ли спокойные character beats;
- меняют ли choices что-то кроме текста кнопки;
- создаёт ли финал конкретный вопрос, ради которого хочется продолжить.

### UI/UX Discoverability

Проверить:

- понятен ли следующий игровой объект без знания API;
- не спрятано ли обязательное действие в маленькой иконке;
- телефон и reasoning workspace достаточно крупные;
- first-use систем сопровождается заметным affordance;
- все обязательные кнопки работают на 1366×768.

### Visual Quality

Проверить:

- композицию;
- иерархию;
- читаемость;
- глубину и свет;
- соответствие character lock;
- отсутствие ощущения dashboard/web prototype;
- качество первого key-art экрана.

Любой FAIL означает, что работа продолжается.

## Visual QA

Для UI, персонажей, CG и игровых сцен недостаточно проверить код.

Обязательно оценить:

- композицию и визуальную иерархию;
- читаемость текста и контраст;
- плотность информации;
- отсутствие случайных UI-артефактов внутри артов;
- соответствие character lock;
- согласованность масштаба и света персонажей;
- отсутствие дешёвого generic-anime ощущения;
- отсутствие вида «админки/дашборда»;
- минимум desktop 1920×1080 и один 1366×768 viewport.

Production-арт не принимается автоматически только потому, что генерация завершилась. Его нужно открыть, осмотреть отдельно и в реальной сцене.

### Screenshot acceptance для текущего пролога

Минимально:

- menu/key art;
- ordinary-life studio;
- безопасная сторона оцепления;
- первое неконтролируемое Echo;
- первая встреча с Егором;
- дом до reveal Кощея;
- Кощей говорит;
- крупный phone UI;
- крупный home reasoning workspace;
- ending hook;
- menu и phone на 1366×768.

### Безопасный browser QA

Канонический способ получить acceptance screenshots:

```bash
cd web
npm run visual-qa
```

Канонический human-equivalent clickthrough:

```bash
cd web
npm run ui-playtest
```

`ui-playtest` обязан проходить игру кликами по реальному DOM/Chromium hit-testing. Нельзя заменять его вызовами `window.__NOVELLA__.act()`.

Оба runner-а обязаны:

- использовать один Chromium-процесс на проход;
- не запускать параллельные браузеры;
- использовать отдельный временный `user-data-dir`;
- иметь жёсткий общий timeout;
- закрывать Browser/CDP в `finally`;
- при сбое завершать только созданную process group;
- сохранять screenshots только в `web/.qa/`, который не коммитится.

## Gameplay QA

Для каждого нового игрового фрагмента:

- есть понятная цель игрока;
- есть действие игрока, а не только чтение;
- choices соответствуют характеру Катерины;
- нет случайных тупиков;
- будущий детективный gameplay не выдаёт готовую истину одной кнопкой;
- способности дают фрагменты/преимущества с ценой;
- отношения меняются через решения и границы;
- конец сцены создаёт причину продолжить.

Технически полный путь не означает автоматически хороший gameplay.

## Agent-playable contract

Human UI и агент используют одно игровое ядро.

Web baseline публикует:

- `window.__NOVELLA__.observe()`;
- `window.__NOVELLA__.actions()`;
- `window.__NOVELLA__.act(id, payload)`;
- `window.__NOVELLA__.reset()`;
- `window.__NOVELLA__.snapshot()`.

Нельзя создавать отдельную упрощённую логику для тестов, расходящуюся с реальной игрой.

Agent observation не должен раскрывать авторские spoilers, которых Катерина ещё не узнала.

## Git workflow

Если пользователь разрешил Git operations:

- branch создаётся от актуального `main`;
- временные upload/test-файлы не попадают в PR;
- перед PR сравнить branch с `main`;
- PR описывает сделанное и фактическую проверку;
- после self-review и успешного quality gate PR merge-ится в `main`;
- после merge проверить фактический SHA `main` и push-triggered quality gate;
- не оставлять готовую работу только в ветке, если пользователь ждёт результат в `main`.

## Никаких ложных статусов

Запрещено:

- говорить «в main», если merge и проверка `main` не выполнены;
- говорить «игру проверил», если она не запускалась;
- говорить «интересно/логично», если не проведён narrative playtest;
- говорить «арт проверен», если изображение не открывалось;
- говорить «visual QA passed», если acceptance screenshots не открывались;
- выдавать мокап за gameplay;
- выдавать partial implementation за законченный slice.

Web vertical slice — `Пролог: Чужая кожа`.

Он должен содержать:

- художественный полноэкранный start key art с Катериной;
- обычную жизнь/тату-студию до мистики;
- случайный контакт со знаком по дороге домой;
- неконтролируемое первое Echo;
- первую встречу с Егором;
- спокойный домашний beat;
- reveal говорящего Кощея;
- крупный и очевидный телефон;
- домашний reasoning workspace вместо преждевременной «полицейской доски»;
- личный первый вывод и hook;
- agent-playable API;
- automated tests, agent smoke, real UI playtest и screenshot QA.

Следующие чаты развивают baseline, а не возвращают старую rushed-investigation логику без отдельного решения пользователя.
