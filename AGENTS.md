# AGENTS.md — обязательный протокол разработки

Этот файл обязателен для любого нового чата/агента, который меняет `Gorills/novella-game`.

## Сначала прочитать

Перед изменениями агент обязан прочитать:

1. `AGENTS.md`;
2. `docs/CANON.md`;
3. документы, относящиеся к задаче;
4. `docs/03-production/QUALITY_GATE.md`.

Если задача касается персонажей или артов — дополнительно `docs/00-vision/VISUAL_BIBLE.md` и `docs/01-narrative/CHARACTERS.md`.

## Приоритет источников истины

При конфликте информации действует порядок:

1. последнее явное решение пользователя по этому проекту;
2. `docs/CANON.md`;
3. locked visual reference / character sheet;
4. world/character/story documents;
5. код и тестовые данные;
6. старые рабочие заметки.

Случайный текст в коде, мокапе или старом документе не может молча менять канон.

## Катерина — жёсткий visual lock

`web/assets/katerina.webp` — канонический исходный референс Катерины.

Обязательно:

- **каре**;
- тёмно-красные волосы;
- карие глаза;
- светлая кожа;
- узнаваемое лицо и пропорции из исходного референса;
- высокая плотность татуировок;
- чёрная современная готическая одежда;
- серебряные украшения.

Запрещено:

- менять каре на длинные волосы;
- «переосмыслять» лицо;
- генерировать новую Катерину вместо locked reference без прямого запроса пользователя;
- принимать арт, где персонаж визуально стал другим человеком.

Если любой текст проекта противоречит этому пункту — этот пункт и `docs/CANON.md` имеют приоритет, а противоречие нужно исправить.

## Definition of Done

Нельзя сообщать пользователю «готово», пока не выполнен quality gate.

Для заметной игровой/визуальной задачи обязательны:

1. реализовать функциональность;
2. запустить tests/validation;
3. реально запустить игру;
4. пройти изменённый игровой путь от входа до выхода;
5. снять реальные screenshots ключевых состояний;
6. открыть и визуально просмотреть screenshots;
7. исправить найденные проблемы;
8. повторить tests + smoke playthrough;
9. проверить diff и состав файлов;
10. открыть PR;
11. убедиться, что PR mergeable и проверки зелёные, либо явно объяснить отсутствие CI;
12. merge в `main`, если пользователь заранее разрешил merge;
13. только после этого считать задачу завершённой.

Если среда не позволяет выполнить один из gate-пунктов, агент обязан прямо сказать какой именно. Нельзя подменять проверку предположением.

## Visual QA

Для UI, персонажей, CG и игровых сцен недостаточно проверить код.

Обязательно оценить:

- композицию и визуальную иерархию;
- читаемость текста и контраст;
- плотность информации;
- отсутствие случайных UI-артефактов внутри артов;
- соответствие character lock;
- согласованность масштаба и света персонажей;
- отсутствие дешёвого generic-anime ощущения;
- отсутствие вида «админки/дашборда» там, где должна быть игровая сцена;
- минимум desktop 1920×1080 и один более узкий desktop viewport.

Production-арт не принимается автоматически только потому, что генерация завершилась. Его нужно открыть, осмотреть отдельно и в реальной сцене.

## Gameplay QA

Для каждого нового игрового фрагмента:

- есть понятная цель игрока;
- есть действие игрока, а не только чтение;
- choices соответствуют характеру Катерины;
- нет случайных тупиков;
- расследование не выдаёт готовую истину одной кнопкой;
- способности дают фрагменты/преимущества с ценой;
- отношения меняются через решения и границы, а не только через скрытый love score;
- конец сцены создаёт причину продолжить.

Минимум один полный автоматизированный agent playthrough обязателен для merge нового slice.

## Agent-playable contract

Human UI и агент используют одно игровое ядро.

Web baseline публикует:

- `window.__NOVELLA__.observe()`;
- `window.__NOVELLA__.actions()`;
- `window.__NOVELLA__.act(id, payload)`;
- `window.__NOVELLA__.reset()`;
- `window.__NOVELLA__.snapshot()`.

Нельзя создавать отдельную упрощённую логику для тестов, расходящуюся с реальной игрой.

Agent observation не должен раскрывать авторские spoilers, которых Катерина ещё не узнала.

## Git workflow

Если пользователь разрешил Git operations:

- branch создаётся от актуального `main`;
- временные upload/test-файлы не попадают в PR;
- перед PR сравнить branch с `main`;
- PR описывает сделанное и фактическую проверку;
- после self-review и успешного quality gate PR merge-ится в `main`;
- не оставлять готовую работу только в ветке, если пользователь ждёт результат в `main`.

## Никаких ложных статусов

Запрещено:

- говорить «в main», если merge не выполнен;
- говорить «игру проверил», если она не запускалась;
- говорить «арт проверен», если изображение не открывалось;
- выдавать мокап за gameplay;
- выдавать partial implementation за законченный slice.
