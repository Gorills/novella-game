# AI-playability и проверяемость игры

## Цель

Проект должен позволять не только человеку играть через графический интерфейс, но и автоматизированному агенту проходить игру, выбирать действия, исследовать сцены, строить гипотезы, проверять последствия и воспроизводить найденные ошибки.

Это не вспомогательный тестовый слой «когда-нибудь потом», а архитектурное требование с первого vertical slice.

# Два равноправных интерфейса

```text
               Game Core
        state / actions / events
              /         \
             /           \
      Human UI          Agent Driver
      Ren'Py             structured API
```

Оба интерфейса вызывают одинаковые игровые действия. Нельзя реализовать отдельную «облегчённую тестовую игру», поведение которой отличается от пользовательской.

# Предварительное техническое направление

Для первого прототипа:

- Ren'Py 8.x — презентация, сцены, экранный UI, диалоги, визуальные переходы;
- Python — чистое игровое ядро;
- сериализуемое состояние;
- deterministic/random-seed режим;
- отдельный agent driver;
- screenshot-based визуальные проверки поверх реального рендера.

Если vertical slice покажет, что проект требует существенно более свободного пространственного gameplay, решение о движке можно пересмотреть до масштабирования контента. До этого момента foundation исходит из Ren'Py + Python core.

# Контракт игрового ядра

Минимальная концептуальная поверхность:

```text
reset(seed, checkpoint?) -> state
observe() -> observation
available_actions() -> action[]
act(action_id, payload?) -> transition
snapshot() -> snapshot_id
restore(snapshot_id) -> state
```

Названия могут измениться в коде, смысл — нет.

# Observation

Агент не должен читать внутренние секретные переменные сюжета, если игрок их ещё не знает.

Наблюдение делится на:

## Player-visible state

- текущая глава/сцена;
- видимые персонажи;
- доступные игровые действия;
- известные Катерине факты;
- найденные улики;
- активные гипотезы;
- доступные способности;
- заметные последствия strain/contamination/exposure;
- текст/варианты текущего диалога.

## Test-only diagnostics

Доступны только в специальном режиме проверки:

- invariant violations;
- transition trace;
- event log;
- stable state hash;
- RNG seed;
- идентификаторы условий, открывших/закрывших действие.

Сюжетные секреты не должны случайно попадать в обычный `observe()`.

# Действия

Каждое действие имеет стабильный семантический ID.

Примеры:

```text
scene.inspect.alley.symbol
scene.inspect.alley.phone
dialogue.egor.ask_why_here
dialogue.egor.refuse_help
seal.trace.use_on.phone
investigation.link.symbol.archive_scheme
location.leave.alley
```

ID не зависит от координат кнопки на экране.

Графический интерфейс может иметь hotspot, анимацию или drag-and-drop, но в ядре это действие остаётся явным.

# Transition

Каждый переход должен позволять увидеть:

- какое действие принято;
- какие player-visible состояния изменились;
- какие события были созданы;
- куда перешёл игровой flow;
- был ли применён RNG;
- возникло ли нарушение инварианта.

Это необходимо для воспроизведения багов.

# События

Минимальные типы событий:

- `ClueDiscovered`;
- `HypothesisCreated`;
- `HypothesisRefuted`;
- `RelationshipChanged`;
- `BoundarySet`;
- `BoundaryRespected`;
- `BoundaryViolated`;
- `SealAwakened`;
- `SealUsed`;
- `StrainChanged`;
- `ExposureChanged`;
- `EchoContaminationChanged`;
- `LocationUnlocked`;
- `SceneEntered`;
- `SceneCompleted`;
- `MajorChoiceCommitted`.

Названия могут быть адаптированы в реализации, но изменения не должны существовать только как случайные присваивания переменных в UI.

# Инварианты

Автоматическая проверка должна ловить минимум:

- найденная улика не исчезает без сюжетно зафиксированной причины;
- гипотеза не может ссылаться на неизвестную Катерине улику;
- недоступная печать не используется;
- одноразовое событие не срабатывает повторно после reload;
- обязательная сюжетная сцена не становится недостижимой из-за допустимой комбинации выборов;
- отказ от романтики не блокирует центральное расследование;
- отсутствие необязательной улики не создаёт hard lock;
- восстановление save даёт эквивалентное состояние;
- одинаковый seed + одинаковая последовательность действий дают одинаковый логический результат;
- визуальный выбор и agent action вызывают один и тот же transition.

# Автоматизированные типы прохождений

## Happy-path

Прохождение центрального расследования с достаточным количеством улик.

## Low-trust Egor

Катерина почти не доверяет Егору, отказывается от романтики, но должна иметь возможность закончить игру.

## High-intimacy / healthy boundaries

Романтическое прохождение с высоким доверием и уважением границ.

## Power-heavy

Игрок использует способности при каждой разумной возможности. Проверяются strain, contamination и exposure.

## Power-light

Игрок избегает магии и по максимуму использует обычное расследование.

## Wrong-hypothesis

Игрок систематически строит правдоподобные, но ошибочные версии. История должна fail-forward, а не ломаться.

## Completionist

Попытка собрать максимум доступных материалов.

## Minimal-evidence

Проверка, что игра остаётся проходимой с минимально допустимым набором ключевых улик, но финал отражает неполноту расследования.

# Agent play session

Цель — позволить задавать тест не как набор заранее написанных кликов, а как задачу:

> «Пройди пролог и первую главу, не доверяй Егору и не используй магию, пока без неё можно продолжать».

Агент получает только player-visible observation, выбирает одно из available actions и продолжает до цели/блокировки.

Таким образом можно тестировать не только известный сценарий, но и реальную агентность внутри механик.

# Визуальная проверка

Логическая автоматизация не заменяет рендер.

Для ключевых checkpoints сохраняются реальные screenshots:

- первая полноценная сцена Катерины;
- первое пробуждение печати;
- первая встреча с Егором;
- экран расследования;
- режим Эха;
- ключевая романтическая сцена vertical slice.

Проверяется:

- композиция;
- отсутствие обрезанных элементов;
- читаемость текста;
- корректность слоёв/поз;
- отсутствие случайных placeholder assets;
- соответствие визуальному состоянию логическому состоянию игры.

# Repro bundle

Любой найденный агентом баг должен по возможности сворачиваться в:

```text
build/version
seed
start checkpoint
ordered actions
final state hash
relevant event trace
screenshot(s)
expected result
actual result
```

Такой пакет позволяет исправить проблему без попытки вручную повторить длинное прохождение.

# Запреты архитектуры

Нельзя:

- прятать сюжетно важную логику внутри Ren'Py screen action;
- использовать координаты мыши как единственную идентичность действия;
- хранить отношения только в локальных переменных конкретного диалога;
- определять найденные улики по тому, был ли показан конкретный экран;
- иметь отдельные условия для UI и agent driver;
- давать агенту скрытые сюжетные ответы в обычном режиме;
- строить механику, которую невозможно восстановить из save/state.

# Definition of done для новой механики

Механика не готова, пока:

1. человек может использовать её через UI;
2. агент может увидеть допустимые действия и выполнить её через тот же core;
3. состояние сериализуется;
4. есть минимум один автоматический сценарий;
5. ключевое визуальное состояние можно зафиксировать screenshot;
6. ошибка воспроизводится по action trace.
