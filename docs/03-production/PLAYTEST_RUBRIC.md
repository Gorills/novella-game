# Playtest Rubric — обязательная оценка игрового опыта

Этот документ обязателен для любого заметного изменения сюжета, UI/UX, артов или игрового потока.

Техническая проходимость **не равна** качественной игре.

После каждого заметного gameplay/visual изменения агент обязан реально пройти изменённый путь и отдельно вынести четыре вердикта:

1. Narrative Logic;
2. Interest & Pacing;
3. UI/UX Discoverability;
4. Visual Quality.

Если любой блок FAIL — работа не считается готовой к merge.

---

# 1. Narrative Logic

## Обязательные вопросы

### Мотивация

- Почему персонаж делает это **сейчас**?
- Есть ли причина, показанная игроку до действия?
- Делал бы разумный человек с опытом этого персонажа нечто подобное?
- Не используется ли «любопытство» как универсальное оправдание опасного поведения?

### Компетенции

- Не ведёт ли себя Катерина как полицейская, криминалист, маг или охотник до того, как получила соответствующий опыт?
- Если она замечает деталь, объясняется ли это её профессией/опытом?
- Не трогает ли она потенциальные доказательства без причины?

### Знание персонажей

- Знает ли персонаж только то, что мог узнать к этому моменту?
- Нет ли реплик, которые требуют информации из будущих сцен?
- Не угадывает ли Катерина правильный ответ слишком быстро?

### Cause → effect

Для каждого крупного beat должно быть возможно одним предложением объяснить:

> «Это произошло потому, что…»

Если событие существует только потому, что следующей сцене нужен переход, это narrative defect.

### Поведение в опасности

Опасность не делает Катерину трусливой, но реакция должна оставаться человеческой:

- страх/сомнение существуют;
- риск осознаётся;
- есть причина не уйти;
- последствия риска ощущаются.

## PASS condition

Ни одного крупного действия без понятной мотивации и ни одного скачка профессиональной компетенции.

# 2. Interest & Pacing

## Scene purpose

Каждая сцена должна делать минимум одно из трёх:

- раскрывать персонажа;
- менять понимание загадки;
- заставлять игрока принять решение/совершить действие.

Сцена, которая только переносит игрока к следующей сцене, должна быть сокращена или наполнена смыслом.

## Reveal budget

Не более одного крупного reveal подряд без эмоциональной или бытовой паузы.

Игрок должен успеть:

- понять новое;
- увидеть реакцию Катерины;
- совершить действие;
- только потом получить следующий крупный поворот.

## Mystery rule

Хороший reveal отвечает на маленький вопрос и создаёт более точный новый вопрос.

Плохой reveal:

- просто добавляет ещё одну случайную странность;
- объясняет слишком много;
- не меняет решения игрока.

## Choice quality

Choices должны:

- менять тон/отношение/сохранённую деталь/будущий контекст;
- оставаться внутри характера Катерины;
- не быть тремя перефразировками одной реплики;
- не предлагать очевидно глупый вариант только ради «agency».

## Hook

В конце игрового отрезка игрок должен уметь сформулировать конкретный вопрос, ради которого хочет продолжить.

## PASS condition

Нет ощущения «события несутся списком». Есть хотя бы один спокойный character beat, один качественный surprise и один понятный hook.

# 3. UI/UX Discoverability

## First-use affordances

Новая важная система не может впервые появляться только как маленькая иконка без подписи.

При первом использовании:

- телефон получает заметное уведомление/подсказку;
- рабочий стол/разбор фактов вызывается крупным сюжетным действием;
- интерактивные области имеют понятный визуальный affordance;
- player goal формулируется коротко и естественно.

## Target size

Основные интерактивные элементы должны быть визуально и физически крупными. Для desktop нельзя прятать сюжетно обязательное действие в иконке около 32–36 px в углу экрана.

## Hierarchy

На экране одновременно должно быть понятно:

1. что сейчас важно;
2. что можно сделать;
3. что является атмосферным декором;
4. где находится текст/реплика персонажа.

## Modal systems

Телефон и домашний рабочий стол — полноценные игровые объекты:

- занимают достаточно места;
- читаются без напряжения;
- не выглядят как маленький widget поверх сайта;
- имеют очевидный способ закрытия;
- не перекрывают критичные действия случайным образом.

## 1366×768

Все обязательные действия должны оставаться видимыми и кликабельными без горизонтального scroll и без обрезанных choices.

## PASS condition

Новый игрок в течение нескольких секунд понимает следующий интерактивный шаг без знания внутреннего API игры.

# 4. Visual Quality

## Первый экран

Menu/key art обязан сам по себе продавать игру:

- Катерина крупно и узнаваемо видна;
- есть художественный фон, а не пустой gradient;
- композиция направляет взгляд к героине и CTA;
- жанр считывается без чтения документации;
- Кощей может присутствовать как часть обычной жизни, не раскрывая твист.

## Scene quality

Проверить:

- композицию;
- глубину кадра;
- свет;
- визуальный фокус;
- масштаб персонажей;
- отсутствие дешёвых UI-рамок вокруг всего подряд;
- согласованность art direction;
- читаемость поверх изображения.

## Character lock

Катерина должна соответствовать locked reference. Каре обязательно.

Кощей: чёрный кот, зелёные глаза. Его нельзя визуально превращать в мультяшного mascot, если остальная сцена не мультяшная.

## Screenshot acceptance

Минимально открыть и вручную проверить:

- menu/key art;
- ordinary-life scene;
- first supernatural contact;
- Egor encounter;
- Koshchey speaking reveal;
- phone;
- home reasoning workspace;
- ending hook;
- минимум два ключевых экрана на 1366×768.

## PASS condition

Экран должен выглядеть как законченная сцена визуальной новеллы, а не как веб-прототип, dashboard или технический макет.

---

# 5. Обязательный итог playtest

Перед merge агент публикует короткий отчёт вида:

```text
Narrative Logic: PASS/FAIL
- причина действий Катерины: ...
- самый слабый логический момент: ...

Interest & Pacing: PASS/FAIL
- лучший beat: ...
- провисающий/слишком быстрый beat: ...

UI/UX: PASS/FAIL
- first-use phone: ...
- primary interaction visibility: ...
- 1366×768: ...

Visual Quality: PASS/FAIL
- лучший экран: ...
- самый слабый экран: ...
- исправления после screenshot review: ...
```

Нельзя ставить PASS без реального прохождения и просмотра соответствующих экранов.
