# Strict Execution Protocol

Этот протокол обязателен для любого агента, который меняет проект. Он существует не для описания желаемого поведения, а для предотвращения повторяющихся ошибок исполнения: зависаний, ложных статусов, слепых повторов tool-call, принятия плохих артов и незавершённого Git workflow.

## 1. Один рабочий контур за раз

В каждый момент активна только одна фаза:

1. PREFLIGHT;
2. IMPLEMENT;
3. VERIFY LOGIC;
4. ART / ASSET PASS;
5. VISUAL QA;
6. FIX;
7. GIT REVIEW;
8. MERGE.

Запрещено одновременно генерировать арты, гонять Chromium, менять код и выполнять серию GitHub-операций. Следующая фаза начинается только после явного результата предыдущей.

## 2. PREFLIGHT обязателен

Перед первой мутацией агент обязан зафиксировать:

- актуальный SHA `main`;
- отдельную branch, созданную именно от этого `main`;
- цель текущего pass;
- Definition of Done;
- затрагиваемые подсистемы и основные файлы;
- какие проверки будут запущены;
- какие screenshots нужны для приёмки.

Если `main` изменился до начала реализации — branch пересоздаётся или актуализируется до изменений, а не молча продолжает работу от старой базы.

## 3. Failure policy: диагностировать, не долбить повторно

После любого сбоя инструмента сначала устанавливается причина.

Правила:

- запрещён слепой повтор того же вызова с теми же условиями;
- один повтор допустим только после установленной причины и реального изменения условий;
- второй одинаковый сбой закрывает этот путь на текущий цикл;
- после второго одинакового сбоя используется альтернативный путь или фиксируется блокер;
- нельзя создавать длинную цепочку «ошибка → повтор → ошибка → повтор».

Примеры:

- Chromium не стартовал / завис → дать timeout и cleanup; локально повторно в этом цикле не запускать; использовать hosted visual QA;
- image generator дважды вернул неверный тип изображения → прекратить генерации, не тратить следующие вызовы на вариации того же запроса;
- GitHub API отверг mutation из-за permissions/schema → исправить конкретную причину; не отправлять серию почти одинаковых вызовов.

## 4. Tool-call budget и checkpoints

Один рабочий блок не должен превращаться в длинную немую цепочку инструментов.

После каждой законченной фазы агент обязан сообщить короткий checkpoint:

- что фактически сделано;
- что проверено;
- что не получилось;
- следующий единственный шаг.

Запрещено писать статус как будто следующая фаза уже выполнена.

## 5. Image / art protocol

Одна генерация должна решать одну конкретную asset-задачу.

Обязательно:

1. сначала определить тип asset: reference sheet, clean background, character cutout, CG и т. п.;
2. запретить UI/text/mockup, если они не являются частью asset;
3. после генерации открыть изображение;
4. проверить в полном размере;
5. только после прохождения art gate помещать в production;
6. отдельно проверить asset внутри реальной сцены.

Запрещено:

- принимать отчётный постер, мокап или contact sheet вместо production asset;
- «спасать» плохую генерацию кропом, если исходник нарушает канон или содержит UI/text artifacts;
- называть персонажа locked до visual review;
- массово производить вариации персонажа до фиксации одного стабильного reference.

### Катерина

`web/assets/katerina.webp` остаётся единственным исходным визуальным lock. Любой новый арт Катерины должен сравниваться с ним. Каре обязательно.

## 6. Browser / Chromium protocol

Для одного QA-pass разрешён один Chromium process tree.

Обязательно:

- unique temporary profile;
- hard timeout;
- `try/finally` cleanup;
- завершение только собственного process group;
- последовательные screenshots;
- отсутствие параллельных browser sessions.

Если локальный browser-run завис или не стал готовым:

1. дождаться timeout;
2. убедиться в cleanup;
3. не запускать локально снова в этом цикле;
4. перейти на hosted visual QA;
5. скачать hosted artifact;
6. реально открыть screenshots перед merge.

Глобальный `pkill chromium` запрещён.

## 7. Implementation protocol

Изменения делаются минимально достаточным цельным pass, а не набором случайных микропатчей.

После реализации обязательна последовательность:

1. `npm test`;
2. `npm run validate`;
3. `npm run agent-smoke`;
4. исправления логики;
5. только после зелёной логики — visual QA.

Нельзя использовать красивые screenshots как доказательство корректного gameplay.

## 8. Visual QA protocol

Visual QA — отдельная фаза после logic gate.

Минимум:

- menu 1920×1080;
- apartment/story 1920×1080;
- investigation 1920×1080;
- Echo 1920×1080;
- Egor encounter 1920×1080;
- evidence board 1920×1080;
- минимум два ключевых экрана 1366×768.

Каждый screenshot должен быть реально открыт и оценён по:

- композиции;
- focal point;
- читаемости;
- масштабу персонажей;
- character consistency;
- clipping/overflow;
- пустым техническим зонам;
- ощущению narrative game, а не web-app/dashboard;
- визуальной химии в dialogue scene;
- отличимости Echo от обычного мира.

Если обнаружен дефект — исправление → повтор соответствующего screenshot. Старый screenshot не считается доказательством исправления.

## 9. Git protocol

Production change всегда проходит:

`fresh main → feature branch → implementation → local logic gates → diff review → PR → CI → hosted visual review → fixes if needed → final diff → merge → verify main`.

Запрещено:

- пушить незавершённый эксперимент в `main`;
- считать branch результатом, если пользователь ждёт `main`;
- merge до visual review для заметной визуальной задачи;
- оставлять временные screenshots, upload chunks, debug assets и helper workflows;
- писать «в main» до проверки actual `main` SHA после merge.

## 10. Stop conditions

Агент обязан остановить конкретный технический путь, а не всю задачу, если:

- один и тот же tool дважды падает одинаково;
- полученный art дважды не соответствует типу запрошенного asset;
- browser-run завис и уже был корректно завершён timeout-ом;
- дальнейшие повторы не добавляют новой информации.

После stop condition выбирается другой способ исполнения.

## 11. Никаких ложных завершений

Разрешены только фактические формулировки:

- `tests passed` — только после реального run;
- `visual QA passed` — только после открытия screenshots;
- `PR ready` — только когда diff проверен и CI завершён;
- `merged to main` — только после merge и проверки SHA `main`.

Нельзя смешивать «планируется», «подготовлено» и «сделано».

## 12. Definition of Done для заметной разработки

Работа закончена только когда одновременно:

- реализован требуемый scope;
- logic tests зелёные;
- полный agent playthrough зелёный;
- реальный visual QA выполнен;
- screenshots открыты;
- найденные дефекты исправлены и повторно проверены;
- diff чистый;
- CI зелёный;
- PR merged;
- проверено, что итоговый commit находится в `main`.

Если хотя бы одного пункта нет, статус — `in progress` или конкретный `blocked`, но не `done`.
